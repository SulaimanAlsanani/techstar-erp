# TechStar CRM backend — مرحلة Staging

يتضمن مجلد `backend` واجهة Cloudflare Worker + D1 لاستقبال طلبات العروض،
ولوحة إدارة عربية محمية بواسطة Cloudflare Access، مع أدوار الموظفين، وسجل تغييرات الحالات.

**الحالة الحالية:** الكود متاح على GitHub لكنه **غير منشور على Cloudflare** ولا يتصل بموقع GitHub Pages. لا تستقبل بيانات عملاء حقيقية قبل إكمال المتطلبات الأمنية والتشغيلية.

## المسارات

| Endpoint | الاستخدام | الحماية |
|---|---|---|
| `GET /health` | فحص الجاهزية الأساسية | عام، دون أسرار |
| `GET /api/content` | محتوى ديناميكي اختياري (فارغ حتى تفعيل CMS) | Origin معتمد |
| `POST /api/leads` | إنشاء طلب عرض مع منع التكرار | Origin + Turnstile + D1 |
| `GET /admin/` | لوحة CRM | Cloudflare Access JWT + قائمة بريد |
| `GET /admin/assets/app.js` | ملف لوحة الإدارة | Cloudflare Access JWT |
| `GET /admin/api/me` | هوية المستخدم ودوره | Cloudflare Access JWT |
| `GET /admin/api/summary` | مؤشرات الطلبات | قراءة/مدير |
| `GET /admin/api/system` | مؤشرات جاهزية الإعدادات دون إظهار الأسرار | مدير فقط |
| `GET /admin/api/leads?status=&q=&due=&assigned=&limit=&offset=` | بحث وفلاتر المتأخر والمجدول والمسند لي | قراءة/مدير |
| `GET /admin/api/leads/:id` | تفاصيل طلب | قراءة/مدير |
| `GET /admin/api/leads/:id/audit` | سجل تغييرات | قراءة/مدير |
| `PATCH /admin/api/leads/:id` | تغيير الحالة مع التدقيق | مدير فقط |
| `PATCH /admin/api/leads/:id/followup` | تعيين موظف وموعد متابعة مع فحص Revision | مدير فقط |
| `GET /admin/api/leads/:id/followup-history` | سجل تعيينات المتابعة | قراءة/مدير |
| `POST /admin/api/leads/:id/complete-followup` | إنجاز متابعة مجدولة مع فحص Revision وسجل مستقل | مدير فقط |
| `GET /admin/api/leads/:id/followup-completions` | سجل مواعيد المتابعة المنجزة والموظف المنفّذ | قراءة/مدير |
| `GET /admin/api/leads/export.csv` | تصدير CSV حتى 500 طلب وفق المرشحات مع تدقيق | مدير فقط |
| `GET /admin/api/exports` | آخر 50 عملية تصدير (من/متى/كم) | مدير فقط |
| `GET /admin/api/leads/:id/notes` | استعراض آخر 100 ملاحظة داخلية | قراءة/مدير |
| `POST /admin/api/leads/:id/notes` | إضافة ملاحظة متابعة حتى 1500 حرف | مدير فقط |

الاستجابة المعتمدة لتأكيد استلام طلب عرض: `{"received":true,"reference":"TS-..."}`.
تجهيز ملخص الطلب في المتصفح **ليس إرسالًا إلى الخدمة**.

### لوحة الجاهزية التشغيلية

يعرض قسم **جاهزية الخدمة الخلفية** داخل CRM حالة وجود إعدادات Cloudflare Access وD1 وTurnstile وRate Limiting، وحالة تفعيل استقبال الطلبات وسياسة الاحتفاظ.

المسار `GET /admin/api/system` متاح للمدير فقط، ويُرجع علامات Boolean دون قيم الأسرار أو رموز الوصول. هذه العلامات تعبّر عن **وجود إعدادات وربط برمجي فقط**، ولا تثبت أن قاعدة البيانات أو Cloudflare يستجيبان بنجاح، ولا أن السياسة القانونية معتمدة. يستمر عرض هوية الموظف الموثق عند عدم توفر قاعدة D1 حتى يمكن تشخيص نقص الإعدادات، بينما تبقى بيانات CRM غير متاحة إلى حين جاهزية القاعدة.

## اختبارات محلية

يتطلب Node.js 22+ وPython 3:

```bash
cd backend
node --check src/index.mjs
node --test test/*.test.mjs
python scripts/check-schema.py
python scripts/check-staging.py
# عند الاستعداد للتجربة على Cloudflare:
python scripts/check-staging.py --require-ready
```

الاختبارات تتحقق من توقيع Access JWT الحقيقي باستخدام مفتاح RSA للاختبار، والصلاحيات، والتصدي لتزوير الهوية، وتغييرات الحالات وتضاربها، وواجهات الطلبات العامة، وعمليات SQLite الفعلية وقيودها وتدقيق التغييرات، وسياسة الحذف الاختيارية.

## نشر مستقل إلى Cloudflare Staging (تشغيل يدوي فقط)

أضيف مسار GitHub Actions باسم [**TechStar Cloudflare staging (manual only)**](../.github/workflows/staging-worker.yml)؛ لا يعمل عند push أو دمج التعديلات، بل فقط عبر `Run workflow` وبعد إعداد حساب Cloudflare.

أنشئ على Cloudflare قاعدة **D1 تجريبية منفصلة** باسم `techstar-leads-staging`، واستخدم اسم Worker `techstar-public-api-staging`. ثم في GitHub أنشئ Environment باسم `cloudflare-staging` وضع فيه المتغيرات التالية:

| نوع الإعداد | الاسم | القيمة |
|---|---|---|
| Secret | `CLOUDFLARE_API_TOKEN` | رمز Cloudflare بصلاحيات مقيدة لمورد Staging |
| Secret | `CLOUDFLARE_ACCOUNT_ID` | معرّف حساب Cloudflare |
| Variable | `TECHSTAR_STAGING_D1_ID` | UUID لقاعدة D1 التجريبية فقط |
| Variable | `TECHSTAR_STAGING_RATE_NAMESPACE` | رقم namespace موجب وفريد للتجربة |

عند تشغيل `Run workflow` يمكن اختيار **Apply migrations** إذا أردت تطبيق الـMigrations على D1 التجريبية؛ الافتراضي **false**. يبدأ المسار بتشغيل الاختبارات، ثم توليد `.wrangler-staging.toml` مؤقت ومهمل من Git، وبعد التحقق ينشر Worker التجريبي فقط. لا يغيّر إعدادات الموقع المنشور على GitHub Pages ولا يرسل بيانات حقيقية إلى D1 تلقائيًا.

**قفل إلزامي:** `LEAD_INGESTION_ENABLED = "false"` في كل إعدادات Staging. يبقى `POST /api/leads` معطّلًا عمدًا حتى لو كانت قاعدة البيانات وTurnstile مجهزتين. سيظهر `ready:false` في `GET /health` بهذا الوضع، وهو سلوك متوقع وليس فشلًا بالنشر.

لتحضير ملف Staging على جهاز موثوق من دون نشره:

```bash
export TECHSTAR_STAGING_D1_ID="UUID-للقاعدة-التجريبية"
export TECHSTAR_STAGING_RATE_NAMESPACE="1002"
python backend/scripts/prepare-staging.py
python backend/scripts/check-staging.py --config backend/.wrangler-staging.toml --require-ready
```

هذا الفحص **لا يتحقق من صلاحية رموز Cloudflare أو من تشغيل Access/Turnstile**؛ يجب اختبارها على Staging بعد إعدادها. لا تفعّل استقبال الطلبات أو تربط الموقع العام حتى تُعتمد الضوابط التشغيلية وسياسة الخصوصية وأذونات الوصول.

## تهيئة Cloudflare قبل التجربة

1. اعتمد الجهة المسؤولة عن بيانات العملاء والبيان القانوني وفترة الاحتفاظ والنسخ الاحتياطي والإجراءات التشغيلية.
2. أنشئ قاعدة D1 باسم `techstar-leads` واستبدل `REPLACE_WITH_YOUR_D1_DATABASE_ID` بالمعرّف الحقيقي في `wrangler.toml`.
3. طبّق ملفات `migrations/0001_leads.sql` ثم `migrations/0002_crm_audit.sql` ثم `migrations/0003_crm_followup.sql` ثم `migrations/0004_crm_exports.sql` ثم `migrations/0005_crm_notes.sql` ثم `migrations/0006_followup_completions.sql` بالترتيب على **بيئة Staging أولًا**.
4. أنشئ Cloudflare Turnstile واضبط `TURNSTILE_SECRET` سرًّا، و`TURNSTILE_HOSTNAME` و`ALLOWED_ORIGINS` على نطاق الموقع المعتمد.
   اضبط كذلك معرّف namespace رقميًا وفريدًا في `[[ratelimits]]` داخل `wrangler.toml`. يُطلب الآن ربط `LEAD_RATE_LIMITER` قبل استقبال أي طلب: الحد الابتدائي 6 محاولات في 60 ثانية لكل IP وفق حدود Cloudflare التقريبية. غياب الـBinding يمنع الاستقبال ويجعل `/health` يُرجع `ready:false`. راجع سياسة الحد المناسبة قبل الإنتاج.
5. أنشئ تطبيق Cloudflare Access يحمي `/admin/*` على نطاق الـWorker، ويقتصر على موظفي الشركة المصرح لهم. **لا تعتمد على إخفاء رابط /admin**.
6. اضبط إعدادات Access التالية عبر أسرار Worker أو متغيرات بيئة إدارية، دون كتابتها في ملفات عامة:

| إعداد | مثال توضيحي | الوظيفة |
|---|---|---|
| `ACCESS_ISSUER` | `https://your-team.cloudflareaccess.com` | جهة إصدار JWT |
| `ACCESS_AUD` | Audience من لوحة Cloudflare Access | التحقق من التطبيق |
| `CRM_ADMIN_EMAILS` | قائمة مفصولة بفواصل | مديرون يغيّرون الحالات |
| `CRM_VIEWER_EMAILS` | قائمة مفصولة بفواصل | قراءة فقط |

يفحص الـWorker توقيع JWT بخوارزمية RS256 من مفاتيح Cloudflare، ثم مطابقة جهة الإصدار وAudience والمدة والبريد مع القائمة المعتمدة. **أي نقص في الإعدادات يؤدي إلى رفض الدخول**.

7. اختبر مسارات الإدارة بموظف إداري، وموظف قراءة فقط، ومستخدم غير مصرح به. اختبر عدم ظهور بيانات CRM في الموقع العام.
8. بعد مراجعة معدل الطلبات، والنسخ الاحتياطي، والرقابة التشغيلية، واعتماد بدء جمع البيانات، يصبح تفعيل `LEAD_INGESTION_ENABLED=true` قرارًا صريحًا **لبيئة الإنتاج المعتمدة فقط**؛ لا تغيّر إعداد Staging الذي يجب أن يبقى مغلقًا. ثم اربط عنوان الخدمة المنشورة في `window.TECHSTAR_CONFIG.apiBaseUrl`، ومفتاح Turnstile العام في `turnstileSiteKey`.

### قوائم العمل والمتابعات المستحقة

في لوحة CRM يستطيع الموظف استخدام مرشح `due=overdue` لعرض المتابعات المتأخرة، و`due=upcoming7` لعرض المواعيد المستحقة خلال الأيام السبعة القادمة، و`due=scheduled` لعرض المواعيد المجدولة، و`due=unscheduled` لعرض الطلبات دون موعد.

تُحسب المقارنات وفق توقيت UTC في SQLite وبتنسيق ISO 8601، ويستبعد مرشح التأخير والأيام السبعة الحالات المغلقة `won` و`lost` و`archived`. يمكن النقر على بطاقتي مؤشرات التأخير والأسبوع المقبل لفتح قائمة الطلبات المفلترة مباشرة. لا يُعتبر العدد تذكيرًا مرسلًا للموظف؛ لا توجد إشعارات خارجية مفعّلة حتى الآن.

### إنجاز المتابعة المجدولة

يتيح CRM للمدير النقر على **إنجاز المتابعة الحالية** بعد انتهاء الاتصال أو الإجراء المطلوب. يتلقى المسار `POST /admin/api/leads/:id/complete-followup` جسم الطلب `{"revision":0}` بعد قراءة آخر إصدار للطلب؛ وعند النجاح يُزيل الموعد الحالي من قائمة المتابعات المفتوحة، مع الاحتفاظ بالموعد السابق واسم الموظف وتاريخ الإنجاز في `lead_followup_completions`.

العملية محمية بصلاحية المدير، وJWT، وOrigin، ورقم Revision لمنع تنفيذ متابعة مرتين أو تأكيد متابعة عدّلها موظف آخر. لا تقبل إكمال طلب ليس لديه موعد، أو طلب مغلق بحالة `won` أو `lost` أو `archived`. عند الحاجة إلى متابعة إضافية يُجدول المدير موعدًا جديدًا.

سجل الإنجاز **لا يقبل التعديل** بعد الحفظ؛ وحذف العميل وفق سياسة الاحتفاظ المعتمدة قد يحذف السجلات المرتبطة به. أضف `0006_followup_completions.sql` إلى D1 التجريبية قبل تفعيل مسارات الإدارة الجديدة.

### تصدير بيانات CRM وملاحظات المتابعة

- يُسمح للمدير بتنزيل ملف CSV يحتوي على **500 طلب كحد أقصى**، مستخدمًا المرشحات المعتمدة نفسها في قائمة CRM. رفض النتائج الأكبر يمنع عمليات التصدير الواسعة غير المقصودة.
- يُجرى **تسجيل التصدير في قاعدة البيانات قبل إرسال الملف**، ويُحفظ اسم الموظف، التوقيت، وعدد السجلات، وفئات المرشحات فقط؛ لا يُحفظ نص البحث في سجل التصدير.
- تضاف علامة حماية إلى خلايا Excel القابلة لتفسيرها كصيغ خطرة، وتُستخدم صيغة UTF-8. لا يعفي ذلك من مراجعة سياسة مشاركة البيانات خارج الشركة.
- سجل التصدير داخل جدول `crm_export_audit` لا يقبل تعديل الصفوف أو حذفها فرديًا. يحتاج مالك النظام إلى سياسة احتفاظ مستقلة ومصرّح بها قبل الإنتاج؛ لا تُعد السجلات خاضعة تلقائيًا لحذف طلبات العملاء.
- ملاحظات العملاء تخزّن في `lead_notes`، ويظهر اسم الموظف وتوقيت الإضافة. لا يمكن تعديل الملاحظة بعد حفظها؛ حذف الطلب ضمن سياسة الاحتفاظ قد يحذف ملاحظاته المرتبطة.
- الواجهة تعرض الملاحظات عبر DOM `textContent`، لا عبر HTML من مدخلات العملاء. الامتناع عن إدخال كلمات السر أو بيانات الدفع أو المعلومات الحساسة في الملاحظات.

### حذف الطلبات المغلقة — معطّل افتراضيًا

يضم `src/retention.mjs` معالجًا لا يحذف إلا طلبات `lost` و`archived` التي تجاوزت مدة محددة، وبحد أقصى 100 طلب في التشغيل الواحد. السجل المرتبط يُحذف مع الطلب بواسطة Foreign Key في D1.

لا يعمل هذا المعالج دون **جميع** الشروط: قاعدة D1، و`CRM_RETENTION_ENABLED=true`، و`CRM_RETENTION_DAYS` كعدد صحيح من 30 إلى 3650، وجدول Cron معتمد. **لا يوجد Cron Trigger معرّف في `wrangler.toml` حاليًا**. لا تُفعّل الحذف قبل اعتماد السياسة قانونيًا وتشغيليًا. يمكن إضافة الجدول بعد الاعتماد في `[triggers]` طبقًا لتوثيق Cloudflare.

### ملاحظات فنية

- ملف `src/admin-app.js` هو مصدر JavaScript لواجهة الإدارة، ويُقدَّم من `src/admin-app.mjs` كنص. اختبارات CI تتحقق من تطابقهما؛ عند تحديث الواجهة يجب تحديث النسختين.
- أي عرض لمدخلات العملاء في الواجهة يتم من خلال `textContent` وليس `innerHTML`.
- يدعم CRM الآن إسناد مسؤول للطلب وموعد متابعة، مع سجل تدقيق منفصل وRevision لمنع تعارض التعديلات. تظهر في اللوحة أعداد المتابعات المتأخرة والمستحقة خلال 7 أيام.
- مرشحات قائمة الطلبات: `due=overdue|scheduled|unscheduled` و`assigned=mine|unassigned`. لا يُستبدل `mine` ببريد مرسل من المتصفح؛ يؤخذ من JWT الموثق.
- طلب تغيير المتابعة يستخدم JSON بالشكل `{"assignedTo":"staff@example.com","followUpAt":"2026-12-11T11:30:00.000Z","revision":0}`. يمكن إفراغ البريد والموعد لإزالتهما. لا يجوز إسناد الطلب إلا لموظف موجود ضمن قائمة الصلاحيات.
- سجلات تغيير الحالات لا تقبل UPDATE بفضل Trigger في SQLite؛ حذف سجل العميل وفق سياسة احتفاظ معتمدة يمكن أن يحذف سجلاته المرتبطة.
- أضيفت حماية Rate Limiting تقريبية على مستوى Cloudflare Worker؛ لا تغني عن WAF أو ضوابط Strict Limits عند الحاجة. لم تُطبّق اختبارات تحميل إنتاجية بعد.
- لا توجد بعد تنبيهات بريد، أو نظام موافقات متقدم، أو نسخ احتياطي معتمد، أو إجراءات إنتاجية معتمدة لحذف/تصدير البيانات بناءً على طلب صاحبها.
- فحص `check-staging.py` يكشف إعدادات قاعدة D1 والحد من الطلبات غير المفعّلة دون تشغيل الخدمة. لا يتحقق من صلاحيات Cloudflare الفعلية أو صحة الأسرار البعيدة؛ يجب اختبارها في Staging.
- ملفات الخط التجارية لا تُرفع إلى GitHub العام؛ تفعيل DIN Next Arabic على جميع الأجهزة يحتاج Webfont مرخّصًا ومُفعّلًا.
